# Проектирование интерфейсов `mattergram_dialog`

Этот гайд задаёт практический контракт для карточек, которые работают как небольшие приложения внутри одного редактируемого поста. Главная метрика — сколько действий и переходов нужно пользователю для завершения частого сценария.

## Бюджет взаимодействия

Используйте эти значения как проектный бюджет, а не как ограничение Mattermost:

- основное действие доступно за 1–2 клика от главного окна;
- вторичное действие — не более чем за 3 клика;
- возврат к предыдущему окну — всегда 1 клик;
- нормальная глубина — до 2 вложенных переходов;
- если частый сценарий требует 4 и более кликов, вынесите его на предыдущий экран или объедините шаги в форму.

Сначала перечислите 3–7 пользовательских сценариев и посчитайте клики для каждого. Сортируйте кнопки по частоте, а не по порядку появления обработчиков в коде.

## Стабильная структура окна

Каждое окно собирайте в одном порядке:

1. заголовок и короткое объяснение;
2. данные или форма;
3. локальные действия над данными: фильтры, сортировка, пагинация;
4. глобальная навигация: справка, настройки, назад.

`Section` задаёт контекст окна. `DataBlock` помещает один объект данных и все локальные действия над ним в один Mattermost attachment. `ButtonRow` используйте только для действий уровня окна, например навигации. У legacy attachment нет серверного лимита в пять действий: клиент переносит кнопки по доступной ширине. Не дробите действия одного объекта из-за искусственного лимита.

```python
Window(
    Section(
        "Сводный отчёт",
        Const("Каждая таблица содержит собственные действия."),
        level=1,
    ),
    DataBlock("Заказы", orders_table, order_filter, order_page_pager),
    DataBlock("Инциденты", incidents_table, incident_filter, incident_page_pager),
    ButtonRow(help_button, settings_button, Back(Const("Назад")), title="Навигация"),
    state=Report.summary,
)
```

Не выносите фильтрацию, пагинацию, редактирование или удаление в соседние attachments. Одинаковые подписи и цвета не создают надёжную связь с таблицей. Локальное действие должно находиться внутри `DataBlock` объекта, который оно изменяет. Основное действие ставьте первым, `Назад` — последним в глобальной навигации. Разрушительное действие называйте явно, например `Удалить отчёт`, а не `Да`.

### Ряды и сетки кнопок

Ряд — это смысловая группа, а не попытка заполнить свободное место. Используйте `ButtonGrid` для нескольких рядов уровня окна и `ActionRow` для явного состава каждого ряда:

```python
ButtonGrid(
    ActionRow(campaigns, new_campaign),       # 2: основные разделы
    ActionRow(pools, proxy_groups),           # 2: инфраструктура
    ActionRow(test_email),                    # 1: главное действие
    ActionRow(nodes, sites),                  # 2: дополнительные разделы
    title="Управление",
)
```

Внутри `DataBlock` каждый переданный control widget образует отдельный ряд. `Filter` автоматически располагается над таблицей, остальные локальные controls — под ней. `DataBlock(table, Filter(...), PagePager(...))` имеет форму `3 / table / 5`. Несколько нижних виджетов одного назначения объединяйте через `ActionRow(...)`; например, `ActionRow(PagePager(...), PageItemSelect(...))` ставит pager и dropdown выбора строки рядом.

Локальные фильтры, пагинация и обычный `ButtonRow` выводятся компактно слева. Равномерное растягивание колонок используется только в `ButtonGrid`, когда несколько равноправных переходов действительно образуют dashboard-сетку.

Правила расстановки:

- один ряд — одно назначение: основные действия, фильтры, пагинация, вторичные или разрушительные действия;
- обычный ряд содержит 2–4 кнопки; стандартный пятиэлементный pager является допустимым исключением;
- одно доминирующее действие можно вынести в собственный ряд;
- опасные действия помещайте в последний отдельный ряд и называйте объект явно;
- не прячьте частое действие за `Ещё` и не добавляйте клики только ради симметрии.

Точная форма рядов является capability Mattermost Blocks. В Blocks каждый ряд рендерится как `ColumnSet` с равными stretch-колонками внутри одного container. Legacy attachments Mattermost 11.1 имеют только плоский массив `actions`, поэтому сохраняют порядок, но переносят кнопки по ширине клиента. Не имитируйте ряды отдельными attachments: это снова оторвёт действия от объекта.

## Выбор пагинации

| Ситуация | Компоненты | Вид | Почему |
|---|---|---|---|
| Известно общее число страниц, важны первый и последний результаты | `PagedList` или `PagedTable` + `PagePager` | `<< < 1/25 > >>` | Полная навигация без дополнительных меню |
| Известно число страниц, места мало | `PagedList` или `PagedTable` + `CompactPager` | `< 1/25 >` | Три стабильные кнопки |
| Таблице нужны три быстрых фильтра и пагинация | `DataBlock` + `Filter` + `PagePager` | активный фильтр цветом над таблицей; `<< < 1/25 > >>` под ней | Все локальные действия остаются в одном attachment; legacy-клиент переносит их по ширине |
| Нужно выбрать видимую строку | `PageItemSelect` рядом с `PagePager` | dropdown и pager под таблицей; выбранная запись раскрывается карточкой ниже | Один action вместо кнопки на каждую строку и без перехода для быстрого просмотра |
| У внешнего API есть непрозрачный cursor, общее число неизвестно | `CursorList` + `CursorPager` | `< Newer  Older >` | Не придумывает несуществующие номера и последний экран |
| Две таблицы в одном окне | два независимых `DataBlock` с разными `id` | таблица и действия внутри каждого блока | Связь видна пространственно, состояния не конфликтуют |

Кнопка текущей позиции всегда отображается, но выключена. На границах выключаются недоступные переходы: строка не прыгает и пользователь не теряет пространственную память.

```python
orders = PagedTable(
    MarkdownColumn("Заказ", "id", max_chars=12),
    MarkdownColumn("Статус", "status", max_chars=12),
    id="orders",
    items="orders",
    page_size=10,
    filter_by="status",
    page_label="Страница {page}/{pages} · всего {total}",
)

DataBlock(
    "Заказы",
    orders,
    Filter(
        id="ordersFilter",
        target="orders",
        options={"Все": None, "Open": "open", "Paid": "paid"},
    ),
    ActionRow(
        PagePager(id="ordersPage", target="orders"),
        PageItemSelect(
            id="ordersSelect",
            target="orders",
            item_id="id",
            item_label="id",
            selection_key="selected_order_id",
            placeholder="Выбрать заказ",
            detail_title=Format("Заказ {item[id]}"),
            detail=Format(
                "**Статус:** {item[status]}  \n**Владелец:** {item[owner]}"
            ),
        ),
    ),
)
```

Для cursor API loader принимает `(cursor, limit, manager)` и возвращает `CursorPage(items, next_cursor)`. Предыдущие cursors сохраняются локально, поэтому возврат не требует поддержки backward cursor на сервере.

## Таблица, список или Blocks

### Markdown-таблица

Используйте `PagedTable`, когда строки сравнивают по одинаковым полям и нужна высокая плотность данных. Это portable-вариант для Mattermost 11.1+.

Ограничения компонента:

- от 2 до 6 колонок; практически лучше 2–4;
- `max_chars` одной ячейки — 4–80;
- сумма объявленных ширин — не более 160 символов;
- не более 25 строк на страницу; для обычной карточки выбирайте 5–15, для мобильного сценария 3–8;
- переносы заменяются пробелами, `|` экранируется, длинная ячейка обрезается с `…`.

Если у записи больше четырёх значимых полей, оставьте в таблице поля для сравнения, а краткие подробности раскройте через `PageItemSelect` карточкой под pager. Отдельное окно или форму используйте для сложного редактирования, длинной истории и самостоятельного маршрута, а не для простого чтения одной записи.

### Markdown-список

Используйте `PagedList`, когда элементы неоднородны, содержат описание, статус или одну главную метрику. Форматируйте одну запись в 1–3 короткие строки. Не имитируйте таблицу пробелами: пропорциональный шрифт разрушает выравнивание.

### Native Blocks

`ColumnSet` из Blocks подходит для компактного summary или пары «метрика — значение» на серверах/клиентах, где профиль явно подтверждает Blocks. Для интерактивного окна capability-probe также должен подтвердить, что бот может заменить `mm_blocks_actions` REST-редактированием собственного поста; рендер без обновляемого реестра годится только для статического содержимого. Полный путь переходов проверен на Mattermost 12.0.2. Это не семантическая таблица. Для длинных наборов строк и Mattermost 11.1 выбирайте Markdown-таблицу. Mattermost Blocks позволяют явно собирать несколько горизонтальных рядов внутри одного контейнера; официальный предел — 50 зарегистрированных действий и 100 блоков на пост. Legacy actions не дают гарантированных разрывов строк и переносятся клиентом по доступной ширине.

Публичный `ActionTable` описывает компактную псевдотаблицу Blocks: 2–4 ограниченные
`ActionColumn` и 1–3 подписанных `RowAction` в каждой строке. Все действия записи остаются
локальными; выбранный `item_id` записывается в `dialog_data[selection_key]` перед переходом.
Например:

```python
ActionTable(
    ActionColumn("Заказ", "id", max_chars=12),
    ActionColumn("Статус", "status", max_chars=12),
    id="orders",
    title="Заказы",
    items="orders",
    item_id="id",
    selection_key="selected_order_id",
    actions=(
        RowAction("Edit", "Изменить", Order.edit, style="primary"),
        RowAction("Delete", "Удалить", Order.delete, style="danger"),
    ),
)
```

Экран «Заказы» в `examples/dialog_navigation_bot.py` использует эту декларацию.
«Изменить» открывает native form выбранного заказа, «Удалить» — отдельную форму
подтверждения. Шесть строк дают 12 локальных действий; вместе с двумя кнопками
навигации пост регистрирует 14 действий. Этот Blocks-only layout намеренно отклоняется,
если профиль ниже 11.11 или `MmBlocksEnabled` не включён: скрытого legacy fallback нет.

Один экран старайтесь удерживать в пределах примерно 1200 видимых символов и двух таблиц. Это UX-бюджет: при превышении добавьте окно подробностей или пагинацию.

## Фильтры

Для 2–5 взаимоисключающих значений используйте `Filter` внутри `DataBlock` целевой таблицы. Фильтр всегда располагается над таблицей, текущее значение выделяется нативным цветом `primary` без `✓` в подписи, а смена фильтра сбрасывает только эту таблицу на первую страницу. Пагинацию оставляйте в том же блоке под таблицей. Если пользователь должен выбрать одну из строк текущей страницы, добавьте `PageItemSelect` рядом с pager: dropdown занимает одно действие и не превращает каждую строку в отдельную кнопку. Задайте `detail_title` и `detail`, чтобы выбранная запись раскрывалась вложенной карточкой сразу под этой строкой; при смене страницы или фильтра карточка скрывается, если выбранной записи больше нет среди видимых строк. Используйте полный `PagePager`, когда важны первая и последняя страницы; `InlinePager` выбирайте только ради компактности.

Если вариантов больше пяти:

- частые 3–4 значения оставьте быстрыми кнопками;
- полный набор перенесите в `Select` формы;
- поисковый или динамический набор загружайте через dynamic data source, если профиль сервера это поддерживает.

## Выбор полей формы

| Данные | Виджет | Правило выбора |
|---|---|---|
| Короткий текст, email, число, URL | `TextInput` | одна строка, задайте subtype и `max_length` |
| Комментарий или описание | `TextArea` | многострочный текст, задайте разумный лимит |
| Одно значение из списка | `Select` | особенно если вариантов больше пяти |
| Несколько значений | `MultiSelect` | теги, участники, каналы |
| 2–4 взаимоисключающих видимых варианта | `Radio` | выбор виден без раскрытия списка |
| Несколько видимых флагов | `CheckboxGroup` | независимые параметры |
| Один boolean | `Checkbox` | согласие или включение функции |
| Только дата | `DatePicker` | дедлайн без времени |
| Дата и время | `DateTimePicker` | встреча, запуск, SLA; задайте интервал |
| Файлы | `FileInput` | один или несколько файлов; сначала проверьте профиль capability |

Для большого объёма ввода:

- показывайте не более 5–7 логически связанных полей на шаг;
- объединяйте поля по задаче, а не по типу данных;
- для 8 и более полей используйте 2–4 окна формы с понятными названиями шагов;
- заполняйте безопасные defaults;
- после сохранения показывайте краткое подтверждение и прямой путь к следующему действию;
- не создавайте вложенную цепочку модальных окон: вернитесь в редактируемый пост и откройте следующий шаг оттуда.

Defaults могут быть статическими или вычисляться во время каждого render из getter-data.
Для строк используйте `Format`, для любых типов — `F[...]`, sync или async getter:

```python
FormWindow(
    TextInput(id="owner", label="Владелец", default=Format("{owner}")),
    Checkbox(id="enabled", label="Включено", default=F["enabled"]),
    MultiSelect(
        id="sources",
        label="Источники",
        options=source_options,
        default_values=lambda data, manager: data["sources"],
    ),
    title=Const("Редактирование"),
    state=Order.edit,
    getter=load_order,
)
```

Результат заново проходит native field validation: динамический default, отсутствующий среди
static options, не отправляется молча, а завершает render явной ошибкой.

## Навигация

`Back` хранит реальный путь, а не фиксированный state. Если пользователь открыл Справку из Заказов, он вернётся в Заказы; если из Инцидентов — в Инциденты.

```python
ButtonRow(
    SwitchTo(Const("Справка"), id="help", state=Report.help),
    OpenForm(Const("Настройки"), id="settings", state=Report.settings),
    Back(Const("Назад")),
    title="Навигация",
)
```

Главный экран должен давать прямой доступ к частым веткам. Не заставляйте пользователя проходить «Главное → Разделы → Отчёты → Тип отчёта», если тип отчёта можно показать на главном экране.

## Live-обновление через WebSocket

WebSocket — источник события, а редактирование поста выполняется через REST. После изменения прикладных данных откройте сохранённый dialog context и вызовите `manager.show(ShowMode.EDIT)`. Renderer заново соберёт текст и все signed actions, поэтому не редактируйте только `message`, теряя `props`.

Если Blocks callback требует deferred REST edit после ACK, перед остановкой приложения вызовите
`await runtime.drain()`: метод ждёт все запланированные edits и возвращает ошибку доставки,
вместо того чтобы терять её в фоновой task.

```python
@dispatcher.message(F.text == "dialog live")
async def refresh(message: Message) -> None:
    application_state.revision += 1
    async with DialogManager(
        dialog_storage,
        storage_key,
        registry,
        renderer,
        actor_id=message.user_id,
        event=message,
    ) as manager:
        await manager.show(ShowMode.EDIT)
```

Полный runnable-сценарий находится в `examples/dialog_navigation_bot.py`: он показывает несколько окон, две независимые Markdown-таблицы в сводке, Blocks-строки с edit/delete на экране заказов, full/cursor pagination, фильтры, typed forms и WS-to-REST refresh.

## Длительная задача и прогресс

Для загрузки, парсинга и импорта используйте `Progress` внутри локального `DataBlock`.
Компонент всегда выводит числовой процент/счётчик вместе с полосой, поэтому состояние не
кодируется одним цветом. Если total неизвестен, не показывайте выдуманный процент: передайте
только `current`, и компонент отобразит indeterminate-состояние с числом обработанных объектов.

```python
DataBlock(
    "Импорт",
    Progress(
        current="done",
        total="total",
        label=Format("{stage}"),
    ),
    Button(
        Const("Отменить импорт"),
        id="cancelImport",
        on_click=cancel_job,
        style="danger",
        when="can_cancel",
    ),
)
```

`DataBlock` поддерживает read-only состояние: когда `can_cancel` становится ложным и кнопка
скрывается, заголовок и прогресс остаются в том же attachment/container. Старый callback
`Button` одноразовый: повтор уже использованного подписанного действия получает outdated ACK и
не запускает callback второй раз.

Для нового интерактивного виджета не требуется менять `DialogRuntime`. Виджет объявляет
`PostControl(action="refresh", widget_id=...)` и реализует async
`process_action(WidgetAction, event, manager) -> WidgetActionResult`. Runtime проверяет
actor/channel/post/intent/state и подпись, затем делегирует widget-local семантику. Верните
`accepted=False` для устаревшего локального token или `target_state=...` для перехода после
успешного применения. Имена action ограничены стабильным lowercase identifier; `switch`,
`back` и `next` зарезервированы для глобальной навигации.

`DialogRuntime.start(...)` возвращает `DialogRef` для post-based окна. Сохраните reference рядом
с durable job и передавайте worker snapshots через публичный REST refresh:

```python
ref = await runtime.start(event, Job.progress, initial_job_data)
if ref is None:
    raise RuntimeError("progress state did not create a post")

applied = await runtime.update(
    ref,
    {"phase": "running", "done": 620, "total": 1000, "stage": "Парсинг"},
    revision=42,
)
```

`update()` проверяет intent/post reference, изменяет `dialog_data`, редактирует тот же post и
заново создаёт signed actions. Монотонная `revision` хранится в actor-scoped dialog transaction;
запоздалый snapshot возвращает `False` и не перезаписывает новое состояние даже при нескольких
worker-процессах.

Для частых обновлений используйте process-local `CoalescingDialogUpdater`: он оставляет только
последнюю ожидающую revision и ограничивает REST update заданным интервалом. Durable job state
по-прежнему хранится в прикладном storage; helper не является очередью задач или scheduler.

```python
async with CoalescingDialogUpdater(runtime, interval=1.0) as updates:
    updates.submit(ref, 40, parsing_snapshot)
    updates.submit(ref, 41, newer_snapshot)  # revision 40 не отправится
    updates.submit(ref, 42, terminal_snapshot, immediate=True)
```

`drain()` и выход из context manager немедленно отправляют trailing snapshot и возвращают
transport error вызывающему коду. `immediate=True` используйте для terminal
`succeeded`/`failed`/`cancelled`; обычные snapshots отправляйте примерно раз в 0.5–2 секунды.

Полная декларация без запуска инфраструктуры: `examples/dialog_progress.py`.

## Проверка перед выпуском

- Частый сценарий укладывается в бюджет кликов.
- Заголовок, данные, локальные действия и навигация визуально разделены.
- Каждая таблица или запись находится в одном `DataBlock` со своими фильтрами, pager, edit/delete и другими локальными действиями.
- Для каждого объекта все действия остаются в одном блоке; искусственного лимита в пять кнопок нет.
- Blocks-пост укладывается в 50 зарегистрированных действий и 100 вложенных блоков.
- У каждой таблицы уникальные `id` для данных, фильтра и pager.
- Длинные значения ограничены, широкая таблица заменена окном подробностей.
- `Back` проверен из каждой входящей ветки.
- Live refresh сохраняет действия и обновляет тот же post.
- Прогресс показывает число/процент, частые snapshots объединяются, terminal update не задерживается.
- Поля формы соответствуют типу данных и capability профилю сервера.
- Вычисляемые defaults проходят native validation после разрешения getter-data.
- Пользовательский action реализован через widget protocol без новой type-ветки в runtime.
